# Load and first-route speed, October 2026

SPEED-01. Numbers first, then targets. SPEED-08 changed the load order since: see [its numbers](2026-10-06-speed-08.md). Measured 2026-10-06 on `main` (b93629d) with `pnpm perf:web`. No app code changed.

## What was measured

Each run is a cold visit: a fresh browser context, no cache, no service worker. The city is set as if chosen last time, so the app opens straight into it. After the map draws, the run types a destination, picks the first suggestion and waits for the route.

- **Phone:** Moto G Power (2022) screen, 412 by 914 at 1.75x. CPU slowed 4x on the page's main thread.
- **Network:** Chrome's Fast 4G (9 Mbit/s, 60 ms) with 5 runs per city, and Slow 4G (1.6 Mbit/s, 150 ms) with 3 runs. A desktop pass (no throttling, 3 runs) shows what is network and what is CPU.
- **Server:** `apps/web/out` with the headers from `vercel.json`, and brotli for text as Vercel does. Bytes are counted by the server, as sent.
- **Figures** are the median, with the range in brackets. Raw runs are in the three JSON files beside this one.

Repeat with `pnpm web:build && pnpm perf:web` (options at the top of `scripts/perf-web.mjs`).

### What the figures mean

| Metric | How it is read |
|---|---|
| First contentful paint (FCP), largest contentful paint (LCP) | The browser's own paint timings |
| City graph loaded | The "Where to?" box appears, which only happens once the routing worker has the graph and posts "ready" |
| Map drawn | The first frame after the base map arrives that makes 150 or more WebGL draw calls (7 for the bare ground, about 75 with the base map's layers and no tiles, 280 to 350 once tiles paint) |
| Destination to route | A click on the first suggestion until "Why this way?" is on screen |
| Worker setup after download | From the last of the worker's files landing to "ready": unzip, parse, join buses, build the router, post places |

### Limits of these numbers

- **The worker is not slowed.** Chromium's CPU throttle only slows the page's main thread. A fixed loop took 1.2 s in a worker at 1x and 1.1 s at 4x, against 0.16 s and 0.74 s on the main thread. So worker setup and the routing itself run at desktop speed here. A Moto G Power's cores are several times slower, so treat "worker setup" and the route times as best cases. Scaling worker setup by 4 gives about 10 s for Edinburgh, 2 s for the other two.
- **No GPU.** The container draws the map in software, so "map drawn" is a ceiling. The ordering between cities and runs is still fair.
- **Local server.** Real CDN latency, HTTP/2 and brotli levels differ. The Vercel connector can list the project but only fetches page text, with no timings or byte counts, so there is no production run. Do one with WebPageTest or a real phone (SPEED-12).
- **One route per city.** The same journeys as the e2e check.

## What the numbers say

1. **Download is the cost, not CPU.** Under Fast 4G the "city graph loaded" time tracks total bytes: about 15.6 s for 15.3 MB, 5.7 s for 5.5 MB and 8.9 MB. On Slow 4G it scales with bytes again (56 s, 14 s, 12 s). The desktop pass, with no network limit, loads the same city in 2 to 5 s.
2. **The base map is the biggest part and it competes with the graph.** It is 61% of Edinburgh's bytes, 49% of Newcastle's and 71% of London's. The app downloads each city's whole `.pmtiles` file (`loadBasemap` reads the full array buffer) in parallel with the graph, so the two share the same bandwidth, and "Where to?" waits behind tiles nobody has looked at yet. Newcastle's whole base map is 2.7 MB; Edinburgh's is 9.2 MB.
3. **The map draws last, and late.** On Fast 4G it appears 6 to 8 s after the search box in the smaller cities and 8.5 s after it in Edinburgh. London on Slow 4G draws at 43 s against 12 s for the graph, because its 6.3 MB base map is fetched whole before any tile can show. (The map time includes software drawing, see the limits.)
4. **First contentful paint is fine** at 0.6 to 0.9 s everywhere. LCP is the "Where to?" box arriving, a second after the graph.
5. **A route takes 1.4 to 1.8 s in Newcastle and London and about 5.4 s in Edinburgh** at 4x (3.4 s on desktop). It does not depend on the network. The router's own cost is within the budget in `PERF_BASELINE.md`; the rest is probably the worker round trip, the trade-off searches and the main thread drawing the route and panel (not separated yet, see SPEED-10). The worker is not slowed here, so on a real phone Edinburgh will be slower than 5.4 s.
6. **The search index is as large as the graph in the smaller cities.** 1.3 to 1.5 MB, against 643 KB (Newcastle) and 402 KB (London) of graph. It is already gzipped, so it cannot shrink further without being cut down.
7. **JavaScript is a steady 650 to 680 KB** after brotli. MapLibre is the largest chunk. It is not city specific.
8. **Worker setup is small except in Edinburgh.** 0.4 to 0.9 s for the other cities, 2.6 s for Edinburgh at desktop speed.

## Is SPEED-06 (a binary graph format) worth doing?

Not now. Gzipped JSON graphs are 25% of Edinburgh's download, 12% of Newcastle's and 5% of London's. Even a graph half the size would take about 1.9 MB off Edinburgh's 15.3 MB (13 points of the total) and under 0.3 MB off London's. The same time is saved by not downloading base map tiles that haven't been looked at yet, with no change to the graph format.

What a binary format would also fix is Edinburgh's worker setup (2.6 s, perhaps 10 s on a phone). That is the one reason to keep it. Do SPEED-08 and SPEED-09 first, then measure again. If Edinburgh's worker setup on a real phone is over 5 s, SPEED-06 earns its place for Edinburgh.

## Proposed targets

The test is the same cold, Fast 4G, 4x CPU visit as above, and Slow 4G for the last column.

| Metric | Now (Edinburgh, Fast 4G) | Target |
|---|---:|---:|
| "Where to?" ready (LCP) | 16.8 s | 6 s or less in every city; 20 s or less on Slow 4G |
| Map drawn | 24.1 s | 8 s or less |
| Bytes before the search box works | 15.3 MB | 6 MB or less (graph, search index, JavaScript) |
| Bytes before the map first draws | 15.3 MB | 2 MB of tiles or less |
| Destination to route | 5.4 s | 3 s or less |

They become roadmap rows, SPEED-08 to SPEED-12, plus a change to SPEED-03 below. They are not budgets yet: SPEED-03 turns the ones that hold into CI checks.

## New roadmap rows

- **SPEED-08:** Load the graph and search index before the base map, so "Where to?" doesn't wait for tiles. Expected: Edinburgh from 15.6 s to under 6 s. The base map starts when the graph is in.
- **SPEED-09:** Read the base map in byte ranges instead of downloading the whole file, and fill the rest in the background for offline. pmtiles already reads ranges. Expected: first view needs a fraction of 9.2 MB. The service worker stores whole responses, so this needs a decision on offline (check D-numbers on offline before building).
- **SPEED-10:** Cut the main thread work after the route returns (5.4 s in Edinburgh against 3.4 s on desktop). Find which of the route draw, the panel and the trade-off searches cost most, with a trace.
- **SPEED-11:** Trim JavaScript: see what is in the 650 to 680 KB (MapLibre, cmdk, vaul, the `/review` code, SPEED-04) and load what the first screen doesn't need later.
- **SPEED-12:** Run this on a real mid-range Android phone and on a real CDN (WebPageTest or Richard's phone), and measure repeat visits and city switching, which this pass didn't. It checks the 4x factor and the unslowed worker.
- **SPEED-05** (smaller search index) now has numbers: 1.3 to 1.5 MB, the same size as or bigger than the graph. Target 600 KB or less.

## Things found on the way

- `serve-out.mjs` serves uncompressed text, so a size count through it overstates JavaScript. `perf:web` has its own server with brotli, copying its header code. The two should share one (small tidy for later).
- The graph is fetched by the worker and the base map by the main thread, both when the app starts. Nothing sets a priority, so the browser shares bandwidth between them.
