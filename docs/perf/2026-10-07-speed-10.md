# The wait after choosing a destination, before and after (SPEED-10)

Measured 2026-10-07 with `pnpm perf:web`: Fast 4G (9 Mbit/s, 60 ms), CPU 4x slower, 5 cold runs per city. The method and its limits are in [2026-10.md](2026-10.md). "Before" is `main` at 26185e1 (after SPEED-08), measured today on the same machine. "After" is this branch. Raw runs: [before](2026-10-07-speed-10-before.json), [after](2026-10-07-speed-10-after.json).

Edinburgh meets the 3 s target, just. The other figures (graph loaded, LCP, map drawn, bytes) are within run-to-run noise of before.

The map also draws 0.9 to 2.9 s sooner, because the network now goes to MapLibre once at load, not again on each redraw. That is part of SPEED-14's busy main thread.

## How it was traced

`pnpm perf:web --trace <dir>` records a Chrome trace of each run from the click on the suggestion to "Why this way?", saves it, and prints the busy time per thread and the busiest functions. Tracing slows the run (the CPU profiler is costly), so traced times are longer than the table's. Use it to see where time goes, not to measure.

## What the trace showed (Edinburgh, before)

1. **The main thread was busy for the whole wait.** About 3.6 s of it was MapLibre serialising GeoJSON to send to its worker, and MapLibre's worker spent about 1.5 s cutting it into tiles again. The source was the city's whole footway network. `MapView` set every source in one effect, so any change to the journey (the destination marker, your position, the route itself) sent the network again. In Edinburgh it is large. Now the network is drawn only when the network, the slope colours or the contrast change.
2. **The router took about 2 s, unslowed.** Most of it was the route searches in `alternatives` (up to ten A* runs), each costing every edge and node again. They now share one cost memo per call: the same routes and the same settled node counts, about a third faster (557 to 382 ms in Node for this journey). `explain` and the trade-offs use other profiles, so they can't share it.
3. **The base map was still loading when the route was asked for.** That answers SPEED-08's question. After the map's first full frame, tiles keep arriving and MapLibre repaints for each one. With the base map arriving later since SPEED-08, these repaints and the network re-send fell into the wait and fought over MapLibre's worker. With the re-send gone, every city is back at or under its SPEED-01 time.
4. **What's left in Edinburgh's 3 s:** about 1 s from the click until the route request leaves, waiting for the phone's position behind map repaints. Then about 1.5 s of routing in the worker, then a few hundred ms of map frames and drawing the route panel. In this container each map repaint costs 300 to 600 ms of main-thread compositing, because the GPU is software. A phone's GPU makes that much cheaper, but its CPU makes the worker slower (the worker is not slowed here). So treat 3 s as the harness's figure, not a phone's.

## Tried and dropped

- Not flying the map to your position when you pick a destination (the route frames it anyway). It made no difference: the repaints come from tiles still loading, not from that move.

## Found, not done

- SPEED-15: faster route searches (arrays in place of maps in the A*, fewer searches in `explain` and the trade-offs). The router is now most of the wait.
- SPEED-16: the route request waits about 1 s for the phone's position on a busy main thread.
