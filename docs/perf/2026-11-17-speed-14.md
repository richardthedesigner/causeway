# Edinburgh's map, drawn sooner (SPEED-14)

Measured 2026-11-17 with `pnpm perf:web`: Fast 4G (9 Mbit/s, 60 ms), CPU 4x slower, 3 cold runs per city. The method and its limits are in [2026-10.md](2026-10.md). "Before" is `main` at 59d2965, measured today on the same machine. "After" is this branch. Raw runs: [before](2026-11-17-speed-14-before.json), [after](2026-11-17-speed-14-after.json).

## Results (median, with the range)

| | Before | After |
|---|---:|---:|
| **Edinburgh map drawn** | 13.27 s (12.74 to 13.29) | **11.36 s** (11.05 to 11.49) |
| Newcastle map drawn | 6.38 s (6.23 to 6.45) | **5.70 s** (5.54 to 5.87) |

Edinburgh now meets the 12 s target. Graph loaded and the other routes are within run-to-run noise.

## What the trace showed (Edinburgh, before)

`pnpm perf:web --trace-load <dir>` now records a trace from opening the page until the map draws. Between the graph being ready (7.2 s) and the map drawing (13.3 s):

1. **The base map started late.** Its first range read left at 9.6 s, two seconds after the search index had downloaded (7.7 s), because D-077 held it until the index was *built*. The main thread spent those two seconds building the index and sending the footway network to MapLibre.
2. **Sending the footway network to MapLibre's worker cost about 1.2 s of main-thread work** (MapLibre's own copy of every coordinate, then the post), right when the graph was ready, and its worker then cut it into tiles while the base map's tiles were waiting.
3. **Building the search index cost about 1.2 s** (accents and punctuation stripped from every name). It is needed when you type, not for the map.
4. The rest is compositing the first tiles in software, which a phone's GPU does far faster.

## What changed

- **The base map starts when the search index has downloaded**, not when it is built (D-087, amends D-077). Its range reads run while the main thread builds the index.
- **The footway network goes to MapLibre once the base map has drawn** (its first `idle`), not as soon as the graph is ready. It is an overlay: the base map shows the streets meanwhile.
- **Network colours are a paint expression on each line's slope bin**, so turning slopes on or off, high contrast and theme changes no longer send the network again.

## Tried and dropped

- **A blob URL for the network**, so MapLibre's worker reads and parses it and the page never copies it. MapLibre 6 sends GeoJSON loaded from a URL back to the page after loading it, so the copy just moved: Edinburgh's map was no sooner.
- **Sending the network as the first base map tiles paint**, not at `idle`. The route came 0.2 s sooner when a destination is picked straight away, but the map drew 0.6 s later.

## Found, not done

- SPEED-17: the network still costs about a second of main-thread work when it is sent. A route asked for in that second waits for it (in the harness, which picks a destination as soon as the map draws, the route took 2.2 to 2.9 s across runs). Prebuilt vector tiles for the network, or a MapLibre source that doesn't round-trip the data, would remove it.
- SPEED-18: build the search index in a worker. It is about 1.2 s of main-thread work on a slowed phone, and the page is sluggish meanwhile.
