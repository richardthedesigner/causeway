# Load order, before and after (SPEED-08)

Measured 2026-10-06 with `pnpm perf:web`: Fast 4G (9 Mbit/s, 60 ms), CPU 4x slower, 5 cold runs per city. The method and its limits are in [2026-10.md](2026-10.md). "Before" is `main` at 6a46dba, measured again today on the same machine, since `main` has moved since SPEED-01. "After" is this branch. Raw runs: [before](2026-10-06-speed-08-before.json), [after](2026-10-06-speed-08-after.json).

## What changed

D-076. The graph and the files that join it download first and together. The search index follows once the graph is ready. The base map follows once the index is built.

## What the numbers say

1. **Edinburgh's "Where to?" comes 5 s sooner, but misses the 6 s target.** The graph is 7.6 s against 12.9 s; LCP is 8.8 s against 13.9 s. Newcastle and London were already under 6 s and are now 0.4 s quicker.
2. **Where Edinburgh's 7.6 s goes**, from one run's file timings: the page's JavaScript and the router worker have loaded by 2.1 s, the graph download (3.8 MB) runs from 2.1 s to 5.8 s, and the worker unzips, parses and indexes it until about 7.4 s. That last 1.6 s is at desktop speed (Chromium doesn't slow workers), so a phone will be slower. Getting to 6 s needs both:
   - the graph download to start before the page has hydrated, not at 2.1 s (SPEED-13), and
   - less work in the worker after the download (SPEED-06, a binary graph).
3. **The side files were the biggest single cost.** Buses, footways, notes, greenspace and works came one after another after the graph, adding about 2 s of round trips in Edinburgh. They now come with the graph.
4. **Fetching the search index alongside the graph was slower.** Tried and measured: Edinburgh's graph ready at 9.4 s against 7.5 s, because unzipping the index on the slowed main thread holds up the page. So the index waits for the graph. The search box shows "Loading places…" for about a second in Edinburgh before search answers.
5. **Newcastle and London were downloading Edinburgh's search index too.** The page starts on the default city and switches to the saved one a moment later, and the index fetch had already started. That is the 1.27 MB that has gone from their totals. Waiting for the graph fixes it.
6. **The map draws later**, by 2.7 to 5 s, because it starts last. That was the trade asked for. SPEED-09 (reading the base map in ranges) is the fix.
7. **Destination to route is 0.3 to 0.7 s slower in every city.** The router, the graph and the order of joins are unchanged. The likeliest cause is the base map still loading and drawing when the route is asked for, since it now arrives later. Not proven; SPEED-10 should trace it.

## Checked on the way

- Before the index arrives, search makes no live lookups (D-025): `PlaceSearch` only asks Photon once the index exists.
- If the graph fails, the base map loads anyway, so the map still draws.
- A city switch doesn't release the new city's map early with the old city's index.
- Repeat visits and city switching were not measured (SPEED-12).

`perf:web --debug` now prints when each file started and finished, which is how point 2 was read.
