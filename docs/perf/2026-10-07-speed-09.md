# The base map in byte ranges, before and after (SPEED-09)

Measured 2026-10-07 with `pnpm perf:web`: Fast 4G (9 Mbit/s, 60 ms), CPU 4x slower, 5 cold runs per city. The method and its limits are in [2026-10.md](2026-10.md). "Before" is `main` at 26185e1 (SPEED-08), measured again today on the same machine with the same harness. "After" is this branch. Raw runs: [before](2026-10-07-speed-09-before.json), [after](2026-10-07-speed-09-after.json).

The machine was slower today than on 2026-10-06: Edinburgh's map drew at 26.9 s on `main` against 23.3 s in [SPEED-08's numbers](2026-10-06-speed-08.md). Compare the two columns here, not across days.

## What changed

D-079. The base map is read in byte ranges: the header, the directories and the tiles in view. Once the map has drawn and settled, the whole file is fetched in the background, so the service worker caches it for offline as before. The order D-077 set is unchanged: graph, then search index, then base map.

The harness now serves byte ranges the way Vercel does, and prints how much had downloaded when the map drew.

## What the numbers say

1. **The target is met for the base map.** 234 to 430 KB of it downloads before the map draws, against 2.3 to 8.8 MB. The 2 MB target holds in every city.
2. **London's map draws 5 s sooner, Edinburgh's 7 s sooner.** Newcastle gains only 0.6 s, because its whole file was 2.3 MB: bytes were never its cost.
3. **Edinburgh still draws at 20 s, and the cost is now the main thread, not the network.** From one run's file timings: the search index lands at 9.9 s, the first range read starts at 14.5 s, and the first tile is asked for at 19.7 s. A CPU profile of that window (4x slower) shows:
   - building the search index on the main thread, which D-077 waits for before releasing the base map (about 4.5 s);
   - MapLibre posting the footway network GeoJSON to its worker, about 2.3 s. `MapView`'s redraw sends the whole network again on every change of route, marker or toilet, not just when the network changes;
   - React rendering, about 1.5 s, and adding the base map's style layers, about 0.5 s.
   Before this change the 8.8 MB download hid all of this. SPEED-14 is the follow-up; the network re-send may be part of SPEED-10.
4. **Destination to route is 0.1 to 0.4 s slower, inside the run-to-run range.** The likely cause is the background fill: the whole file is downloading when the harness picks a destination, since it does so right after the map draws. A person would take longer than the harness to pick one. Not proven.
5. **Total bytes for a visit don't fall.** The whole file is still fetched once, for offline, plus the ranges read first (about 0.2 to 0.4 MB more). The "transferred" figures in the raw runs stop when each run ends, part way through the fill, so they are lower than the real total.

## Checked on the way

- Vercel serves the file in ranges: on the production deployment, `Range: bytes=0-16383` returns `206`, `Accept-Ranges: bytes`, a strong ETag and the same bytes as the file. No hosting change is needed.
- Offline: in Chromium with the service worker on, after one visit the whole file is in the cache. With the network off, a reload draws the map, and every range read comes back `206` from the service worker, cut from the cached file.
- A host that ignores Range, a range read that fails (for example an old service worker that can't store a partial response), and the base64 preview host all fall back to the whole file, which is how it loaded before. Unit tests: `apps/web/test/basemap-source.test.ts`.
- If the file changes between reads (the weekly data refresh), the ETag differs and PMTiles reads the header again.
- Repeat visits were not measured (SPEED-12).
